CVX Documentation

A Git-compatible version control engine written in Rust. Own your history, keep your data portable, and use the same repository format as Git without a runtime dependency on the Git binary.

Built for compatibility

CVX stores standard Git objects, indexes and refs in .cvx/. Git can read the same repository with --git-dir=.cvx, and CVX can open existing .git/ repositories directly.

Object formats
SHA-1 and SHA-256
Transports
local, HTTPS, SSH
Control directory

Production status: beta

CVX is usable for local workflows and controlled automation, but Phase 10 is still open. Do not use it as the only copy of critical production data. Read the roadmap and the compatibility matrix before adopting it.

What CVX is

CVX is an independent implementation of the Git repository model. It reads and writes the same object database, index and reference files, so your history stays portable. The binary does not shell out to git; Git is used by the test suite as a compatibility oracle.

The engine is split into small crates: object parsing, pack codecs, index formats, refs, revision walking, diffing, merging, transports, repository operations and the CLI. The cvx binary composes those crates into a single workflow.

Portable by default

No proprietary object format and no hidden conversion step. A CVX repository is a Git repository.

Explicit failure

Unsupported formats, corrupt data and unsafe paths fail with a named error instead of being silently ignored.

Small surface, sharp edges

Every command is implemented, tested against Git where practical, and documented with its limits.

Quick start

Install from source with a current stable Rust toolchain, then create a repository. The default control directory is .cvx/; use --storage git when another tool expects a literal .git/ directory.

1

Build the binary

shell
cargo build --release -p cvx-cli
./target/release/cvx version
2

Create and commit

shell
mkdir demo && cd demo
cvx init
printf "hello\n" > hello.txt
cvx add .
cvx commit -m "initial commit"
cvx log --oneline
3

Clone over a real transport

cvx clone https://github.com/marcosgabrielgomes110-collab/cvx.git cvx-copy
CVX_SSH_KEY=~/.ssh/id_ed25519 cvx clone git@github.com:marcosgabrielgomes110-collab/cvx.git cvx-copy
Identity. Commit identities are read from user.name and user.email, or from CVX_AUTHOR_NAME, CVX_AUTHOR_EMAIL, CVX_COMMITTER_NAME and CVX_COMMITTER_EMAIL.

Operational examples
shell
# Verify and compact a repository
cvx fsck --strict
cvx gc --prune

# Repair a missing or corrupt index
cvx fsck --repair

# Inspect the last change on a branch
cvx log --oneline -n 5
cvx diff HEAD~1..HEAD --stat

Architecture

The CLI is a thin layer over repository operations. Each arrow below is a real crate boundary; the object database, index and refs are standard Git files.

The transport layer never invokes the Git binary. Local paths are opened as repositories; HTTPS and SSH speak protocol v2 and receive-pack.

Objects, refs and the worktree

Objects

Blobs, trees, commits and annotated tags are stored as standard Git objects. Every object is hashed with the repository's declared format and verified when read. Loose objects are zlib-compressed; packs support version-2 indexes, offset deltas and ref-deltas.

Index and worktree

The index is a standard Git index. Checkout and restore validate paths against the repository root, reject control-directory components and refuse to follow symlinked ancestors. Index writes use index.lock and atomic rename.

References

Loose refs, packed refs, symbolic HEAD, reflogs, tags and refs/remotes are supported. Ref updates use compare-and-swap locks; fetch updates remote-tracking refs and FETCH_HEAD.

Revision resolution

Branches, tags, remote refs, abbreviated object IDs, HEAD~N, HEAD^N and detached HEAD are supported. Ambiguous or missing revisions fail explicitly.

Network and authentication

Network operations use protocol v2 for fetch and receive-pack for push. Pack data is spooled to a temporary file during fetch and streamed from disk during push; thin packs are used when the server advertises support.

AreaBehavior
HTTPSBasic auth through the credential store or environment. Redirects are disabled for authenticated requests. Credentials are refused over plaintext HTTP.
SSHSystem OpenSSH with keys or ssh-agent. Set CVX_SSH_KEY for an identity and CVX_SSH_STRICT_HOST_KEY_CHECKING=yes for strict known_hosts.
TokensGITHUB_TOKEN/CVX_TOKEN are scoped to github.com and *.github.com by default. Set CVX_TOKEN_HOST for another host.
Shallow clone--depth is supported for network clones. Shallow fetch updates and --unshallow are not implemented yet.
Partial clone--filter=blob:none is supported; missing blobs are fetched lazily. Other filters are not validated yet.
Timeout/retryCVX_HTTP_TIMEOUT_SECS and CVX_HTTP_RETRIES control idempotent HTTP requests.
Credential safety. Tokens are read from the environment or stored in the OS keychain, with a user-only file fallback. They are never accepted in repository URLs or sent over plaintext HTTP.

Security and operations

Repository integrity

cvx fsck verifies refs, commits, trees, tags, index entries and dangling objects. --strict also fails on dangling objects. --repair can rebuild a missing or unreadable index from HEAD and, with an explicit age threshold, remove stale locks.

Worktree safety

Checkout refuses to follow symlinked ancestors, never deletes directories recursively, and refuses to overwrite untracked files without --force. Case-insensitive control paths and Windows-reserved names are rejected.

Release integrity

Releases publish checksums and an SBOM. The workflow runs formatting, Clippy and the test suite before builds, verifies the tag against the workspace version, and includes MIT/Apache license texts in archives.

Known gaps

Mandatory signing, build provenance, independent audit, reproducible comparison and full network chaos coverage are still open. The threat model and release checklist document the current boundary.

shell
cvx fsck --strict
cvx fsck --repair
CVX_STALE_LOCK_AGE_SECS=3600 cvx fsck --repair
cvx gc --prune

Roadmap

CVX ships in explicit compatibility slices. The current release is v0.9.4; the roadmap is ordered through 1.0.

  1. v0.9.4

    Security and safety fixes

    Path hardening, bounded parsers, host-scoped tokens, gc locking, commit CAS, dirty-remote protection, atomic config and release gates.

  2. v0.10.0 · in progress

    Phase 10: security, concurrency, durability

    Remaining: mandatory signing/provenance, dependency policy, reproducible comparison, SSH SHA-256 fixture, transactional multi-ref push, shallow/unshallow and network chaos tests.

  3. v0.11.0

    Git completeness and ecosystem

    Submodules, LFS, commit signing, reftable, MIDX, alternates, worktrees, packaging, installers and migration docs.

  4. v1.0.0-rc.1

    Release candidate

    Feature freeze, real-repository soak, signed/reproducible artifacts, rollback and public bug window.

  5. v1.0.0

    Production release

    No open P0 issues, validated security and release gates, supported platforms and a frozen support policy.
